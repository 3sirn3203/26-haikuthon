# Stage 1 — 공통 구성 요소와 조합

자연어 문장화나 이미지 생성 없이, 프롬프트의 의미를 결정하는 구성 요소를 만든다.
Python 3.9 이상과 PyYAML 6.x를 사용하며 GPU·외부 서비스는 필요 없다.

```sh
python3 -m pip install -r stage1_components/requirements.txt
python3 -m stage1_components generate
python3 -m stage1_components generate --id experiment01
python3 -m stage1_components validate --id experiment01
python3 -m stage1_components validate --id experiment01 --check-reproducibility
python3 -m stage1_components generate --id experiment01 --config stage1_components/policy.yaml --output-dir /tmp/mixed-components
python3 -m unittest discover -s stage1_components/tests -v
```

저장소 루트에서 실행한다. 기본 seed는 `20261106`이다. 다른 seed를 쓰면 생성과 검증에
모두 같은 `--seed N`을 전달한다. `--output-dir PATH`로 출력 위치를 바꿀 수 있다.
`--check-reproducibility`는 메모리에서 다시 생성한 두 파일의 바이트를 기존 파일과 비교한다.

`--id ID`는 두 출력 파일의 공통 접미사다. 생략하면 **명령 실행 시각의 KST(UTC+9)**를
`YYYYMMDDHHMM`으로 사용한다. 예를 들어 ID가 `202611141530`이면
`train_components_202611141530.jsonl`, `test_components_202611141530.jsonl`을 생성한다.
ID는 실행 시작에 한 번 정하며, 생성 중 분이 바뀌어도 두 파일에 같은 ID를 사용한다.
명령 출력에 ID와 저장 경로를 표시한다. ID에는 문자·숫자·밑줄·하이픈·점을 사용할 수 있다.
검증할 때는 생성에 사용한 `--id`를 지정한다. 검증 명령에서도 생략하면 현재 KST 분을 사용한다.
같은 ID를 다시 생성하면 해당 두 파일을 교체한다. 기본 ID가 같은 분 안에 다시 실행되어도 같다.

## 유사 묶음 크기 설정

`policy.yaml`의 `group_size_weights`에서 split별 작은 그룹의 **그룹 수 기준 상대 비율**을 정한다.
모든 문항을 유사 그룹으로 만들며 독립 기준 문항은 생성하지 않는다. 기본 설정은 다음과 같다.

```yaml
group_size_weights:
  train: {4: 1, 8: 1}
  test: {4: 1, 8: 2, 16: 1}
test_clusters:
  max_size: 64
```

각 split의 수량 구간·새로움 유형별로 총 행 수를 정확히 유지하면서 목표 비율에 가장 가까운
정수 묶음 수를 고른다. 따라서 작은 구간에서는 실제 비율에 반올림 차이가 생긴다.
기본 설정은 train 4개 그룹 334개·8개 그룹 333개로 총 4,000행,
test 4개 그룹 444개·8개 그룹 888개·16개 그룹 445개로 총 16,000행이다.
0으로 설정하거나 생략한 크기는 생성하지 않는다. 허용 크기는 4·8·16이다.
이전의 단일 맵(`{4: 1, 8: 1, 16: 1}`)도 지원하며 두 split에 동일하게 적용한다.
설정 전체를 생략하면 기존 8개 묶음을 사용한다.
활성화한 크기로 행 수를 맞출 수 없으면 생성 전에 실패한다. 예를 들어 16개만 활성화하면
16의 배수가 아닌 구간은 생성할 수 없다. 반복 category 10%도 묶음 전체 단위로 할당한다.
기존 의미 제약·커버리지·다양성 조건을 만족하는 장면이 부족한 경우에도 사유와 함께 실패한다.

4개는 `2×2`, 8개는 `2×2×2` 또는 `2×4`, 16개는 `2×2×2×2`, `2×2×4` 등의 완전 교차로 구성한다.
두 개 이상 핵심 축이 다른 이웃의 최소 수는 묶음 크기별로 1·3·7개다.
전체 생성·검증에 같은 `--config PATH`와 seed를 사용한다.

Train에는 큰 그룹을 만들지 않는다. 작은 그룹들이 같은 배경/렌더링이나 객체 구성을
공유할 수 있지만, 설명의 명시 조건을 동시에 만족하는 후보는 허용하지 않는다.

Test의 유사 문항은 큰 그룹(cluster)으로 생성한다. 큰 그룹마다 **객체 종류와 변형 템플릿**을
하나 만든다. 작은 그룹 안에서는 객체 종류와 전체 물체 수를 고정한 채 **속성·수량 배분·관계**를
변형한다. 작은 그룹 사이에서는 **배경·화풍·시점·조명**을 바꾸며, 이 네 값은 각 작은 그룹 안에서 고정한다.
객체 종류 교체와 작은 그룹 구별용 고정 속성 추가는 하지 않는다.

같은 큰 그룹에서 크기가 같은 작은 그룹은 객체·속성·수량·관계 변형을 정확히 공유한다.
4·8·16개 크기가 섞이면 최대 크기의 템플릿에서 작은 크기의 완전 교차 부분집합을 고른다.
부분집합도 홀드아웃 반례, 다축 차이, 동일 어휘 후보 조건을 통과해야 한다.
예를 들어 같은 8개 객체 변형을 사진/정면/측광과 색연필/측면/확산광으로 각각 표현한다.

작은 그룹마다 배경·화풍·시점·조명의 **조합이 반드시 달라야** 한다. 각 축도 가능한 범위에서
서로 다른 값을 우선 선택한다. 모든 객체 변형에 호환되는 배경과 화풍만 사용하며,
`inside` 관계의 overhead 시점처럼 필수인 값은 유지한다. 따라서 네 축 모두가 매번 바뀌는 것은 아니다.
커버리지나 변형 비율 보강이 필요하면 큰 그룹 전체를 교체해 공유 템플릿을 유지한다.

`test_clusters.max_size`는 **이미지 수 상한**이다. 작은 그룹을 쪼개지 않고 객체 수·novelty
구간별로 배치하므로 나머지 cluster는 더 작을 수 있다. 각 cluster에는 최소 두 작은 그룹이
있어야 한다. 상한은 4의 배수이고 활성화한 최대 작은 그룹 크기의 두 배 이상이어야 한다.
비율은 split 전체의 목표이며 모든 cluster 내부에 정확히 같은 비율을 강제하지 않는다.
`test_clusters: null` 또는 키 생략은 이전처럼 독립적인 test 작은 그룹을 생성한다.
Train/test 행 수는 수량 설정을 따른다. Test는 16,000개 장면을 이미지 후보로 만들고,
그중 8,000개만 질의로 선택한다. 후보를 제거하거나 그룹을 쪼개지 않는다.

## 이미지 후보와 평가 질의

`test_query_fraction: 0.5`는 각 작은 그룹에서 절반을 질의로 선택한다.
4·8·16개 그룹에서 각각 2·4·8개를 뽑아 총 8,000개 질의를 선택한다.
별도 난수 스트림과 동일 seed로 선택을 재현한다.
각 test 행의 `is_query`가 선택 여부다. Train에는 이 필드를 붙이지 않는다.
설정을 생략하면 이전처럼 질의 선택 메타데이터를 만들지 않는다. 비율은 0 초과 1 이하이며,
각 그룹 크기와 전체 후보 수에 곱한 값이 정수여야 한다.

Stage2는 **후보 전체**의 이미지 생성 프롬프트를 `test_prompts.jsonl`에 저장하고,
`is_query: true`인 행만 같은 ID·문장 그대로 `test_queries.jsonl`에 복사한다.
Stage3에는 전체 후보 파일을 입력한다. 평가에서는 질의 파일 8,000행과 이미지 후보
16,000장을 사용하며, 질의 ID에 해당하는 이미지가 정답이다. 후보 전용 항목의 프롬프트도
이미지 생성에는 필요하지만 평가 질의로 제공하지 않는다.

## 조명 설정

`policy.yaml`의 `lighting_weights`에서 **이미지 수 기준 상대 목표 비율**을 정한다.

```yaml
lighting_weights:
  soft_diffuse: 1
  direct_sunlight: 1
  side_light: 1
  warm_indoor: 1
```

부드러운 확산광, 직사광, 측광, 따뜻한 실내 조명을 사용한다. 직사광은 야외 배경에서만,
따뜻한 실내 조명은 실내 배경에서만 고른다. 확산광과 측광은 두 환경에서 모두 가능하다.
Train과 test 모두 작은 그룹마다 조명을 선택하고 그 안에서는 고정한다.
배경 호환성과 그룹 크기 때문에 실제 비율은 목표와 다를 수 있다.
값이 0이거나 생략한 조명은 사용하지 않는다. 설정 전체를 생략하면 기존처럼 `soft_diffuse`만 쓴다.

## 파일

- `components.yaml`은 legacy에서 가져와 검수한 공통 사전이다. 174종 중 거울을 보류한 173종을 두 split이 공유한다. 객체별 속성·단위·관계 역할·배경·화풍 제약과 비활성 선언을 함께 관리한다.
- `policy.yaml`에서 행 수, 홀드아웃 수, 분포 목표, 검색용 유사 문항의 기준과 seed를 정한다.
- `model.py`는 장면을 검증하고 관계와 범주를 정규화한다. `holdouts.py`는 train에서 제외할 결합과 서로 대조할 수 있는 대안들을 고른다.
- `groups.py`는 크기별 정수 할당과 그룹 식별자를 관리한다. `generator.py`와 `scenes.py`가 train을 조립하고, train에서 실제로 관측된 결합을 이용해 test를 조립한다.
- `clusters.py`는 공통 객체 템플릿과 크기별 부분집합을 만들고 작은 그룹마다 다른 시각적 조건을 적용한다. 보강 시 큰 그룹 전체를 교체하며 크기·novelty·반복 category 할당은 유지한다.
- `coverage.py`는 train에서 드물게 나오는 객체가 다른 장면과 관계 상대를 만나도록 예시를 보강한다.
- `ranking.py`와 `validation.py`는 저장된 구성 요소로 후보 묶음을 복원하고 각 split 전체에서 정답의 구별 가능성을 검사한다.

한 번 실행하면 `outputs_stage1`에 다음 두 파일을 저장한다. 같은 폴더에 다른 ID의 결과와
기존 접미사 없는 component 파일을 함께 보관할 수 있다. 관련 없는 파일·디렉터리가 있으면
실패하며 삭제하지 않는다. 검증과 재현성 비교는 지정한 ID의 두 파일에만 적용한다.

| 파일 | 행 수 | prompt_id |
|---|---:|---|
| `train_components_{id}.jsonl` | 4,000 | `"0000"`–`"3999"` |
| `test_components_{id}.jsonl` | 16,000 | `"0000"`–`"15999"` |

ID는 최소 네 자리이며 10,000부터 다섯 자리로 늘어난다. 질의 샘플링 후에도 ID를 다시 매기지 않는다.

Stage2에서 이 결과를 사용하려면 `stage2_prompt_generation/config.yaml`에
`component_id: "experiment01"`처럼 같은 ID를 설정한다. `component_id`를 생략하면
Stage2는 기존 `train_components.jsonl`, `test_components.jsonl`을 읽는다.

각 행의 필드는 `prompt_id`, `group_id`, `cluster_id`, `entities`, `relations`, `background`, `rendering`이다.
질의를 샘플링한 test 행에는 JSON boolean `is_query`가 추가된다. 그룹 ID와 이 선택 값은
LLM에 전달하는 장면 정보에서 제외한다.
`group_id`는 0부터 시작하는 JSON 정수다. 같은 유사 묶음의 모든 행에 같은 ID를 저장하고,
출력에서 처음 등장하는 그룹 순서대로
ID를 부여하며 train 다음 test로 이어져 두 split 전체에서 중복과 누락이 없다.
행은 섞어서 저장하므로 같은 그룹이 연속된 `prompt_id`를 갖지는 않는다.
기존 `group_id` 없는 입력도 읽을 수 있으며, 이때는 공통 장면 조건으로 묶음을 복원한다.
`cluster_id`는 test의 큰 그룹마다 0부터 순차적으로 부여하는 정수다. Train에서는 `null`이고,
Test의 모든 행은 큰 그룹에 속한다. 같은 큰 그룹의 작은 그룹들은 서로 다른 context를 사용하며 `group_id`로 구별한다.
Stage2에서는 작은 그룹별로 표현 가이드를 배정하며 두 ID를 LLM 장면에 포함하지 않는다.
객체 ID는 없으며 관계의 `subject`/`object`는 해당 행의 객체 배열 인덱스다.
각 관계는 `subject`, `predicate`, `object`만 저장하며, `rendering`은 `style`, `viewpoint`,
`lighting`만 저장한다. 프레이밍, 방향의 기준, 관계 적용 범위는 생성·관리하지 않는다.
기존 파일을 읽을 때도 `framing`, `reference_frame`, `scope`를 제거하며,
Stage2의 생성·검수 LLM에 해당 필드나 제약을 전달하지 않는다.
단위는 공통 사전에서 해석한다. 신발·장갑은 한 짝, 선글라스는 완성된 한 개로 센다.
전체 수량은 테이블·용기·착용 물품을 포함한 모든 `count`의 합이다.

## 정확히 맞추는 할당

| 구성 | 2개 | 3개 | 4개 | 5개 | 6개 |
|---|---:|---:|---:|---:|---:|
| Train 전체 | 1,000 | 1,800 | 1,200 | 0 | 0 |
| Test 전체 | 3,600 | 6,480 | 4,320 | 1,200 | 400 |

- Train 4,000개와 test 후보 16,000개 전체가 유사 그룹에 속한다. 질의 8,000개도 모두 유사 그룹에서 선택한다.
- Test의 각 수량 구간에서 속성 결합만 미관측 40%, 관계 결합만
  미관측 40%, 둘 모두 미관측 20%를 맞춘다.
- 속성 홀드아웃 64개는 32개 객체 각각의 같은 속성 축에서 두 값을 골라 구성한다.
  관계 홀드아웃 512개 중 160개는 같은 객체 쌍에서 바꿔 볼 수 있는 관계 80쌍이다.
  나머지 352개는 서로 다른 객체 쌍에 분산한다.
- 공통 사전의 활성 객체 173종은 train 16문항 이상, test 32문항 이상 등장한다. 저장된 행에서 두 split의 객체 종류를 직접 집계하여 공통 사전과의 일치도 검증한다.
- Train의 각 객체는 **독립 그룹 5개 이상**에 등장하고, **서로 다른 객체 4종 이상과 명시된 관계**를 맺는다. 유사 묶음은 크기와 관계없이 한 단위로 센다. 상대 종류에는 해당 행의 관계 양 끝에 연결된 다른 종류만 포함한다.
- 유사 문항의 10%는 같은 category의 서로 구별되는 그룹을 포함한다.

## 텍스트로 이미지를 검색하는 문항

한 행이 이미지 후보 한 장에 대응한다. `is_query: true`인 행만 텍스트 질의로 제공한다.
평가할 때는 test 이미지 16,000장이 전체 후보이며, 내부의 4·8·16개 묶음은 정답과
혼동할 후보를 설계하는 데 쓴다. 질의를 절반 선택해도 이미지 후보 그룹의 크기는 그대로다.

- 각 유사 묶음은 객체 종류·총 객체 수·배경·화풍·시점·조명을 고정하고, 객체별 수량 재배분,
  속성 교환, 관계 방향 또는 행동 대상 변경을 묶음 크기에 맞게 완전 교차한다. 각 문항에는
  이웃 3·7·15개가 있고, 그중 1·3·7개 이상은 두 가지 이상의 핵심 축이 다르다. 어느 한 축만 보아도
  정답과 같은 값을 갖는 후보가 있다. 같은 종류가 두 그룹이면 고정된 가시 속성으로 구분한다.
- 각 유사 문항에는 객체명·그룹별 수량 값·속성명과 값·관계어의 목록과 등장 횟수가 모두 같은
  다른 후보가 있다. 예를 들어 같은 두 객체를 두고 어느 쪽이 다른 쪽의 왼쪽에 있는지 바꾼다.
  수량과 속성이 어느 객체를 꾸미는지, 누가 관계의 주체인지 고려해야 두 후보를 구별할 수 있다.
- 모든 test 유사 문항에서 홀드아웃 속성을 지우거나 홀드아웃 관계를 지우면, 해당 결합 외에는
  동일한 후보가 하나 이상 남아야 한다. 두 유형이 모두 미관측이면 **각각 따로** 가려서 검사한다.
  이 후보와 앞의 단어 목록이 같은 후보는 서로 다를 수 있다.
- 각 split의 전체 후보에서 같은 배경과 렌더링을 가진 다른 장면이 질의의 명시 조건을 모두
  만족할 수 있는지 검사한다. 질의에 없는 추가 객체를 허용하고, 후보에서 생략한 속성·관계는
  미정으로 취급한다. 명시된 종류별 수량, 속성값 충돌, 관계 방향·행동 대상, 상하위 범주와
  같은 종류의 여러 그룹 간 가능한 대응을 검사한다. 이 검사는 이미지 생성 전 구성 요소에 적용한다.

이전 데이터 검증을 위해 과거 정책의 `train_baseline_counts`, `test_baseline_counts`는
계속 읽을 수 있지만, 현재 정책은 두 항목을 생략하므로 독립 기준 문항을 생성하지 않는다.

Train에 홀드아웃이 없어야 하고, 모든 test에는 최소 하나가 있어야 한다.
그 밖의 test 핵심 결합은 **실제로 생성된 train**에서 관측되어야 한다.
Train의 다양성을 보강할 때는 같은 크기·전체 물체 수의 유사 묶음끼리 교체한다. 원래 결합을 다른 train 예시에서도 배울 수 있는 문항을 먼저 교체한다. Test에 쓸 관측 결합은 보강 전후의 train에 공통으로 남은 결합에서 고른다. 보강에는 별도 난수 스트림을 사용하며 test 파일을 참조하지 않는다.
속성 값과 관계 자체도 train에서 관측되어야 하므로, 새 단어의 등장만으로
조합 일반화 조건을 충족하지 않는다. 수량·배경·화풍의 변경도 홀드아웃으로 세지 않는다.

객체 순서, 좌우·상하 역표현, 인접 관계의 대칭성과 방향 관계의 추이 폐쇄를 정규화한다.
범주의 상위 관계도 홀드아웃 검사에 반영한다. 입력은 사전의 정식 category/predicate만
허용하여 동의어 표기로 검사를 우회할 수 없다. 객체 구성이 같아도 배경·화풍·시점·조명이
다르면 별도 장면으로 허용한다. 객체 구성과 시각적 조건까지 같은 중복은 거부한다.
방향·지지·포함 관계의 순환, 잘못된 참조, 불가능한 역할, 가려진 내용물,
구별되지 않는 동일 category 그룹도 거부한다.

독립 검증 시 `group_id`로 묶음을 읽고 도메인 목록·전체 수량·배경·렌더링의 일치와 ID의 연속성을 검사한다.
Test cluster의 상한·작은 그룹 구성·공통 객체 종류·크기별 변형 집합의 동일성/포함 관계,
작은 그룹별 context 고정 및 그룹 간 context 차이, cluster ID의 연속성도 검사한다.

## 분포와 검수 범위

유사 문항에서 같은 객체 종류 집합은 train 최대 24행, test 최대 128행까지 허용한다.
`ranking.max_inventory_rows`에서 split별로 조절한다(이전의 공통 정수 설정도 지원).
Test는 cluster 안에서 같은 객체 조합을 반복할 수 있어 더 큰 상한을 사용한다.
test 유사 문항에는 서로 다른 객체 집합을 최소 100개 확보한다. 큰 그룹당 객체 집합이 하나이므로
이 최솟값은 큰 그룹 수보다 클 수 없다. 전체 문항에서 개별 객체의
등장 비율 상한은 4.5%이며, 들기·착용·탑승의 주체인 사람은 30%다.
각 split 유사 묶음의 15% 이상에서 수량 재배분, 지지·포함·행동 관계 변경을
각각 검증한다. 두 객체의 속성값 교환은 최소 5%, 한 객체의 속성과 방향만 바꾸는 묶음은 최대 20%다.
두 split 모두 동물과 탈것에 올라탄 장면을 포함하며, 사람이 타는 동물은 서 있는 자세여야 한다.
배경은 모든 등장 객체와 행동에 맞는 장소에서 고른다. 헬리콥터는 공항 계류장에 배치하고,
공구·식기·음식 등을 침대나 소파 위에 배치하는 조합은 제외한다.

관계 계열·주제·화풍에는 train/test에 같은 **목표 비율**을 적용한다. 역할과 배경,
홀드아웃, 최소 빈도 같은 제약 때문에 목표 비율과 실제 비율이 완전히 일치하지는 않는다.
이는 위의 정확한 수량 할당과 구분한다. 주제는 배열의 첫 객체에 의존하지 않고,
각 문항 안의 서로 다른 객체 종류가 속한 domain의 평균 비중으로 집계한다.

콘솔에는 목표 대비 퍼센트포인트 차이, train/test 간 total variation distance,
객체별 빈도·배경·시점·조명·속성 수·관계 수를 재계산한 결과를 표시한다.
추가 보고서나 메타데이터 파일은 만들지 않는다.

공통 사전과 정책이 변경되면 두 파일을 함께 재생성해야 한다. 제약에 맞는 후보가
부족하면 사유와 함께 실패하며, 전체 검증을 통과한 결과만 저장한다.
이 검증은 구성 요소의 일관성과 상대적 구별 조건을 확인한다.
실제 이미지의 충실도와 모델이 느끼는 난이도는 후속 단계에서 평가한다.
