# HAIKUTHON 운영진 베이스라인 종합 요약

**작성:** 이찬 · **작성일:** 2026-11-11 · **기준 커밋:** `0b6075a`

**범위.** 결과를 올린 운영진 4명(이찬, 장서현, 박준현, 정이찬)의 실험을 종합하였다. 나머지 7명의 폴더에는 아직 결과가 없다. 개별 상세는 각 폴더의 README와 [REPORT.md](REPORT.md)에 있다.

**표기.** score = (Recall@1 + NDCG@5) / 2. "추정"은 실측값을 외삽한 값이다. Public = test `7000–7999`(잠정), Private = 나머지.

---

## 1. 결론 요약

1. **과제는 의도대로 동작한다.** zero-shot 0.43 → 파인튜닝 0.68 → 재정렬 0.81–0.84로 단계마다 점수가 오른다. SigLIP2 결과는 다른 장비(L4)에서 같은 값으로 재현되었고(장서현), 다른 모델(FG-CLIP)에서도 같은 경향이 확인되었다(박준현).
2. **현재 제출 서버에는 두 가지 구조적 문제가 있다.** 첫째, 이미지 id가 프롬프트 id와 같아 추론 없이 만점이 가능하다. 둘째, 전체 문항을 한 번에 넘겨받으므로 문항 간 정보 활용(+0.10)을 구조적으로 막지 못한다. 대회 전에 반드시 조치해야 한다.
3. **난이도를 결정하는 실질 변수는 추론 시간 제한이다.** 서버 제한(L4, 15분)에서는 전체 문항 재정렬이 불가능하다. 데이터 난이도(HN 수, 묶음 구조)는 현행 유지가 적절하다.
4. **동일 제출물의 실행 시간이 3배까지 달라진다**(81초 vs 250초). 시간 제한을 엄격히 적용하기 전에 원인을 제거해야 한다.

**교차 검증된 사실**

- **파인튜닝이 가장 큰 단일 이득이다**(+0.25). L4에서 학습 7.6분이면 된다.
- **묶음 단위 배치가 핵심 기법이다.** 같은 묶음의 형제 문항을 한 배치에 넣으면 +0.06(SigLIP2), +0.12(FG-CLIP)를 얻는다.
- **모델 크기는 거의 무관하다.** 0.15B FG-CLIP이 파인튜닝 후 1.14B SigLIP2와 0.007 차이까지 따라온다. 측정된 구성의 피크 VRAM은 모두 12GB 이하이다.
- **train HN과 텍스트 HN은 1단계 학습에 도움이 되지 않는다.** 이미지 HN 추가는 효과가 없었고(이찬), 규칙 기반 텍스트 HN은 오히려 0.015 낮았다(박준현).
- **zero-shot 가중치를 섞으면 손해이다.** WiSE-FT와 점수 앙상블은 0.677을 0.58–0.65로 낮춘다(장서현).
- **재정렬은 K=5가 최적이며 K=10은 더 낮다.** 두 사람이 독립적으로 관찰하였다. 단, 1단계 점수를 융합하거나 재정렬기를 학습하면 K=10이 다시 유리해진다.
- **생성 이미지 선호 모델은 이점이 없다**(PickScore 0.331).

## 3. 출제자 관점의 우려 사항

우선순위 순으로 적는다.

### 3.1 [필수] 제출 서버에서 id로 정답이 드러난다

- 서버는 `predict(model, queries, candidates)`에 `prompt_id`와 `image_id`를 넘긴다.
- 정이찬의 사이트 제출 결과는 "정답 = `prompt_id`와 같은 `image_id`" 규칙으로 채점되었고, 그 점수(0.331)가 로컬 측정과 부합한다. 즉 서버 데이터에서도 두 id가 같다.
- 따라서 모델 없이 `prompt_id`를 그대로 반환하면 만점이 된다.
- **조치:** 서버 데이터의 이미지 id를 무작위로 재부여하고, 후보 순서를 섞는다. 정답 매핑은 채점 측에만 둔다.

### 3.2 [필수] 문항 간 정보 활용을 구조적으로 막지 못한다

- `predict`가 8,000문항과 15,000장을 한 번에 받는다. Hungarian 할당(+0.096), 텍스트로 복원한 묶음 안 할당(+0.084)을 코드 한 줄로 넣을 수 있다.
- 결과 CSV만으로는 탐지가 어렵다. 정직한 상위권 모델도 top-1 중복이 자연히 줄어들기 때문이다.
- **조치(택일 또는 병행):**
  1. 서버 계약을 "후보 인코딩 1회 + 문항별 예측"으로 분리한다. 가장 확실하지만 서버 수정이 필요하다.
  2. 규정에 명시하고 상위 팀의 `model.py`를 수동 검수한다. 약 25팀 규모이므로 상위 5–10팀 검수는 현실적이다.

### 3.3 [필수] 동일 제출물의 실행 시간 변동

- 같은 zip이 81초(웜)와 250초(콜드)로 측정되었다(박준현). 원인은 첫 실행의 스토리지 읽기로 추정된다.
- 15분 제한에서 170초의 변동은 재정렬 가능 문항 수를 크게 바꾼다. 제출 순서에 따라 유불리가 생긴다.
- **조치:** 측정 구간 시작 전에 이미지 파일을 미리 읽어 두거나, 데이터 로딩 시간을 제한에서 제외한다. 사이트가 구간별 시간과 피크 VRAM을 보고하도록 하면 참가자와 운영진 모두에게 도움이 된다.

### 3.4 [권고] HN과 원본이 같은 시드를 공유한다

- 이미지 픽셀만으로 HN–원본 쌍의 78%를 정밀도 98%로 찾을 수 있다(장서현). 쌍이 없는 이미지에는 Public 정답의 94%가 들어 있다.
- 문항 정보를 쓰지 않으므로 현재 규정 문구로 금지되는지 불명확하다. 실제 점수 이득은 측정되지 않았다.
- 시드를 바꿔 재생성하면 HN의 시각적 유사성이 줄어 난이도가 내려갈 수 있다. 재생성 비용도 크다.
- **조치:** 재생성보다 규정 보완을 권한다. "후보 이미지 간 비교로 풀의 구조를 추론하는 행위 금지"를 명시하고 3.2의 코드 검수에 포함한다.
- 3.1의 id 익명화는 시드 역산(`sha256("<split>:<id>")`)을 통한 이미지 재생성 공격도 함께 차단한다.

### 3.5 [권고] 검증 집합 구성에 따라 결론이 뒤바뀐다

- 무작위 val에서는 0.93이 나오지만 test는 0.54였고, 두 조건의 우열도 반대로 나왔다(박준현). 묶음 단위 val로 바꾸자 val과 test의 방향이 일치하였다.
- 참가자 대부분은 무작위 val을 쓸 것이다. 이는 실력 변별 요소로 볼 수 있으나, 다수 팀이 Public 리더보드에만 의존하게 될 위험이 있다.
- **판단 필요:** 과제 설명에 "유사한 문항이 묶음으로 존재한다"는 사실을 알릴지 결정해야 한다.

### 3.6 [확인 필요] 아직 측정되지 않은 것

- 재정렬기 LoRA 학습의 test 성능 (val 0.92–0.94만 있음. val은 HN 비율이 17%로 test의 47%보다 낮아 낙관적이다)
- 15분 제한 안에서의 2단계 end-to-end 실측 점수
- 8B 이상 재정렬기, 검출기 기반 방법
- 일부 융합 가중치는 test 절반에서 선택되어 약간 낙관적이다(장서현 B5)
- v2 프롬프트의 검수 기록 부재(라벨 노이즈 가능성)

## 4. 난이도 조절에 대한 의견

### 4.1 데이터 난이도는 건드리지 않는 것을 권한다

- 예상 점수 분포가 이미 충분히 넓다.

  | 참가자 수준 | 예상 score |
  |---|---|
  | 공개 모델을 그대로 사용 | 0.42–0.44 |
  | train으로 파인튜닝 | 0.55–0.68 |
  | 묶음 구조를 파악하고 2단계 설계 | 0.70–0.84 |

- 최상위 구성도 만점과 거리가 있으므로 상한 포화 위험은 낮다. 재정렬기 학습이 test에서도 통하면 0.85 이상이 가능하나, 이는 시간 제한으로 제어된다.
- HN 수는 난이도를 선형으로 조금 움직일 뿐이다(7,000장에 −0.09). 난이도의 주된 원천은 묶음 구조이며, 이를 바꾸려면 데이터를 다시 만들어야 한다.

### 4.2 실질적인 난이도 손잡이는 시간 제한이다

- **15분(현행):** 전체 재정렬이 불가능하다. 참가자는 가벼운 1단계 모델, 작은 K, 불확실한 문항만 선별 재정렬, 해상도 축소 같은 효율 설계를 해야 한다. 출제 의도(효율과 정확도의 절충)에 가장 부합한다. 다만 재정렬의 이득이 작아져 상위권 점수가 0.68–0.75에 몰릴 수 있다(추정).
- **30분:** 가벼운 구성이면 전체 문항을 K=3으로 재정렬할 수 있다. 2단계 설계의 이득이 뚜렷이 드러나고, 무거운 모델은 여전히 불가능하다.
- **60분 이상:** 4B 재정렬기로도 절반 이상을 처리한다. 효율 설계의 압박이 약해진다.

**권고.** 15분을 확정하기 전에 기준 구성 하나(파인튜닝 FG-CLIP + Qwen3.5-2B, 시간 예산 적용)를 실제 서버에서 end-to-end로 돌려 본다. 1단계 단독 대비 이득이 0.03 미만이면 25–30분으로 완화하는 것이 타당하다. Private 7,000문항의 신뢰구간이 약 ±0.01이므로, 0.03 이상의 차이는 순위로 구별된다.

### 4.3 그 밖의 조절 수단

- **Public 구성.** Public은 Private보다 일관되게 0.04–0.08 높지만 방법 간 순위는 같다. Public 리더보드가 Private을 잘 예측하므로 현행 유지가 무난하다. "Public = 쉬운 문항"을 의도했다면 재선정이 필요하다.
- **train HN 500장.** 제공해도 성능상 중립이다. 참가자가 HN의 성격을 이해하는 데 도움이 되므로 제공을 권한다.
- **모델 크기 제한.** 불필요하다. 24GB와 시간 제한으로 충분하다.
