# HAIKUTHON 숏컷·규정 허점 레드팀 분석

**작성:** 이찬 · **작성일:** 2026-11-12 · **목적:** 악의적인 참가자의 관점에서 "딥러닝 모델 개발"이 아닌 경로로 점수를 올릴 수 있는 방법을 열거하고, 측정 가능한 것은 실측하여 대회 전 조치 우선순위를 정한다.

**전제.**
- 참가자는 `model.py`(`load_model`, `predict`)와 가중치를 zip으로 제출한다.
- 서버는 `predict(model, queries, candidates, top_k=5)`에 8,000문항(`prompt_id`, `prompt`)과 15,000장(`image_id`, `image_path`)을 한 번에 넘긴다.
- GPU 제한은 15분, 제출은 30회이다.
- 이 전제는 참가자들이 작성한 `model.py`와 측정 노트에서 역으로 추정하였다. 서버 코드(`2026-HAIKUTHON`)는 직접 확인하지 못했으므로, **§1의 항목은 HAI 측 확인이 필요하다.**

**측정 기준.** 측정값은 SigLIP2 so400m의 test 전체 임베딩 캐시(zero-shot = zs, 묶음 배치 파인튜닝 = ft)로 계산하였다. 기준점은 zs 0.427, ft 0.680이다.

## 1. 인프라 수준 (서버 확인 필요)

### 1.1 정답 노출 경로 — id를 무작위화해도 남는 것

id만 바꾸고 아래를 놓치면 누수가 그대로 남는다.

| 경로 | 설명 | 조치 |
|---|---|---|
| `image_id` = `prompt_id` | 현재 사이트 채점이 이 규칙으로 동작함(정이찬 제출로 확인) | 무작위 id |
| **`candidates` 목록의 순서** | 원본 0–7999 다음 HN 순서로 넘기면 *목록의 위치 i*가 곧 문항 i의 정답이다. id를 바꿔도 순서가 남는다 | 후보 목록을 매 실행 셔플 |
| `queries` 순서 | 문항 순서와 후보 순서가 함께 정렬되어 있으면 위와 같다 | 문항 목록도 셔플 |
| **`image_path` 문자열** | `.../08000-14999/…` 같은 폴더명이 HN 여부를 알려 준다. 파일명에 원래 번호가 남아도 같다 | 단일 폴더, 무작위 파일명 |
| **파일시스템 메타데이터** | 파일을 원래 순서로 복사·압축 해제하면 inode 번호와 mtime/ctime 순서가 원래 id 순서를 따른다. `os.stat()`만으로 순서를 복원할 수 있다 | 무작위 순서로 기록, mtime 일괄 초기화 |
| `prompt_id` 값 범위 | 현재 Public = 7000–7999이다. 문항 id가 남아 있으면 어떤 문항에 HN이 없는지 알 수 있다(§3과 결합하면 Public만 +0.05) | 문항 id도 무작위화 |
| PNG 메타데이터 | 확인 결과 깨끗함(`IHDR/IDAT/IEND`만) | 유지 |

### 1.2 시간 제한 밖에서 코드 실행

박준현의 측정에 따르면 "unzip·데이터셋 로드·의존성 설치"는 시간 제한에서 제외된다.

- **의존성 설치.** 참가자가 `requirements.txt`나 로컬 패키지를 지정할 수 있다면, 소스 배포판(sdist)의 빌드 스크립트(`setup.py`)는 설치 중에 임의 코드를 실행한다. 이 시점에 test 이미지가 마운트되어 있고 GPU가 보이면, 이미지 15,000장 인코딩이나 재정렬 전체를 **측정되지 않는 시간**에 끝내고 결과를 디스크에 남길 수 있다.
- **모듈 import 시점.** 서버가 타이머 시작 전에 `model.py`를 import하면, 모듈 최상위 코드나 import 시점에 띄운 백그라운드 스레드/프로세스가 측정 밖에서 실행된다.
- **실행 간 상태 유지.** 컨테이너, 볼륨, `/tmp`, HF 캐시가 제출 사이에 유지되면, 한 번의 제출에서 계산한 결과를 다음 제출이 재사용할 수 있다.
- **조치:** 의존성은 서버 고정 이미지만 허용(사용자 패키지 설치 금지) 또는 설치 단계에서 test 볼륨·GPU 미마운트. 타이머는 import 이전부터 시작. 제출마다 새 컨테이너와 빈 임시 디렉터리.

### 1.3 test 데이터 유출

- **네트워크.** 의존성 설치에 네트워크가 필요하다면, 그 단계나 추론 단계에서 test 이미지·프롬프트를 외부로 보낼 수 있다. 유출된 test로 오프라인 학습을 하면 사실상 만점에 가깝게 갈 수 있다.
- **로그와 오류 메시지.** 서버가 stdout/stderr나 예외 메시지를 참가자에게 보여 주면, `print()`로 프롬프트를 흘릴 수 있다.
- **제출 CSV를 통한 은닉 채널.** 출력은 8,000문항 × 5개 id이고, 각 칸은 15,000개 중 하나이다. 칸당 약 14비트이므로 제출 한 번에 약 70KB를 숨겨 내보낼 수 있다. 참가자가 Kaggle에서 자기 제출 파일을 내려받을 수 있다면, 30회 제출로 test 프롬프트 상당 부분을 빼낼 수 있다.
- **조치:** 추론 컨테이너 네트워크 완전 차단. 참가자에게는 점수와 소요 시간만 반환하고 로그·CSV는 반환하지 않는다. Kaggle 제출을 서버 계정으로 하고 참가자에게 파일 접근을 주지 않는다.

### 1.4 채점 구현 허점

| 입력 | 허점 | 조치 |
|---|---|---|
| top-5에 같은 id 반복 | 중복을 그대로 세는 NDCG 구현이면, 정답을 5칸에 모두 넣었을 때 DCG가 1 + 0.63 + 0.5 + 0.43 + 0.39 = **2.95**가 되어 상한(1)을 넘는다 | 중복 제거 또는 실격 |
| 후보에 없는 id | 오류 대신 무시하면 칸 수 조작에 쓰일 수 있다 | 검증 후 실패 처리 |
| 5개 미만 / 초과 | 처리 규칙이 불명확하면 분쟁 소지 | 정확히 5개 강제 |
| 문항 누락 | 0점 처리인지 오류인지 | 0점 처리 명시 |
| 시간 초과 | 부분 결과를 채점하는지, 전체 실패인지 | 규정에 명시 |

참고로 박준현의 `score_csv.py`와 이찬의 `metrics.py`는 첫 등장 위치만 쓰므로 안전하다. 서버와 Kaggle의 실제 채점 코드는 확인이 필요하다.

### 1.5 실행 시간 복권

- 같은 zip이 웜 81초, 콜드 250초로 측정되었다(박준현).
- 시간 예산 안에서 "남은 시간만큼 재정렬"하는 제출은 실행 환경에 따라 점수가 달라진다. 참가자는 같은 zip을 여러 번 제출해 운 좋은 실행을 고를 수 있다.
- **조치:** 이미지 사전 로딩 후 타이머 시작, 또는 리더보드에 마지막 제출이 아닌 "선택 제출"을 쓰게 하고 시간 변동을 줄인다.

### 1.6 서버 GPU 사양 확인

김우진의 T4 측정(Qwen3.5-2B, 쌍당 약 0.30초)은 박준현의 L4 측정(0.067초)보다 약 4.5배 느리다. 서버가 T4라면 15분 동안 재정렬 가능한 쌍은 약 3,000쌍(김우진 추정 2,000회와 같은 규모)이다. 이 경우 2단계 설계의 여지는 더 줄어든다. **서버 GPU가 L4인지 T4인지 확정해야 시간 제한 논의가 의미를 가진다.**

## 2. 문항 간 정보 활용 (규정 위반, 탐지 어려움)

규정은 "한 문항의 예측이 다른 문항에 영향을 주면 안 된다"이다. 아래 방법들은 모두 이를 위반하지만, 코드 한두 줄이라 참가자가 위반인지 모르고 쓰거나, 알고도 "정규화일 뿐"이라고 주장할 수 있다.

**표 1.** 문항 간 후처리의 이득 (test 8,000문항)

| 방법 | 성격 | zs | ft |
|---|---|---|---|
| 정직한 코사인 | 기준 | 0.427 | 0.680 |
| **inverted softmax** (각 이미지를 전체 test 프롬프트에 대해 softmax 정규화, τ=0.02 / 0.01) | 텍스트 측 정규화 | **0.589 (+0.162)** | **0.728 (+0.048)** |
| CSLS (k=10, test 프롬프트 기준 허브 보정) | 텍스트 측 정규화 | 0.510 (+0.083) | 0.718 (+0.038) |
| dual softmax (τ=0.02) | 양측 정규화 | 0.510 (+0.083) | 0.701 (+0.022) |
| 전역 Hungarian (top-50) | 1:1 할당 | 0.523 (+0.096) | — |
| 텍스트로 복원한 묶음 안 Hungarian | 1:1 할당 | 0.511 (+0.084) | — |

τ는 test에서 고른 값이라 상한에 해당한다. 그래도 τ 0.01–0.02 범위에서 모두 큰 이득이 난다.

- **inverted softmax가 Hungarian보다 크다.** 할당이 아니라 정규화라서 "1:1 매칭 금지"로 규정을 쓰면 빠져나간다. 정이찬의 `model.py`에도 dual softmax가 실험 옵션으로 들어 있다. 즉 운영진조차 자연스럽게 떠올리는 기법이다.
- 측정하지 않았지만 더 강할 가능성이 있는 변형: VLM 재정렬 시 같은 묶음 형제 프롬프트를 오답 후보로 함께 보여 주는 listwise 질문("이 이미지에 맞는 설명은 다음 8개 중 무엇인가").
- **결과 CSV로는 탐지가 거의 불가능하다.** 정규화는 top-1 중복률을 크게 바꾸지 않는다.
- **조치:**
  1. 규정 문구를 "다른 문항의 텍스트나 예측 결과를 어떤 형태로든 사용하는 것(정규화, 앙상블 가중치, 할당 포함) 금지"로 구체화한다.
  2. 가능하면 서버 계약을 바꾼다. `encode_candidates(candidates)`를 한 번 호출하고 `predict_one(query)`를 문항마다 호출하는 방식이면 구조적으로 막힌다.
  3. 최소한 상위 팀 `model.py`의 수동 검수.

## 3. 후보 풀 구조 활용 (다른 문항은 안 보지만 출제 의도 우회)

HN은 원본과 같은 시드로 생성되어 구도가 거의 같다. 다른 문항을 보지 않고 후보 이미지끼리만 비교해도 "쌍둥이"를 찾을 수 있다.

- 쌍둥이 검출: 픽셀 썸네일로 정밀도 0.98 / 재현율 0.78(장서현), ft 이미지 임베딩으로 0.81 / 0.60.
- **쌍둥이 헤지**(top-1의 쌍둥이를 2위로): 0.680 → 0.675. 이득 없음.
- **쌍둥이 없는 이미지 가산점:** Public 정답은 HN이 없어 쌍둥이가 없다는 점을 노린다.

  | 가산점 | 전체 | Public | Private |
  |---|---|---|---|
  | 0 (기준) | 0.680 | 0.744 | 0.671 |
  | +0.01 | 0.648 | **0.791** | 0.627 |
  | +0.03 | 0.507 | 0.757 | 0.472 |

  Public만 올리고 Private은 떨어뜨린다. 참가자가 Public 리더보드만 보고 튜닝하면 **Public 점수가 부풀려지는 함정**이 된다. `prompt_id`로 Public 문항을 식별할 수 있으면(§1.1), Public에만 적용해 손해 없이 Public을 올릴 수 있다.
- **조치:** 문항 id 무작위화. Public을 "HN 없는 문항"이 아니라 **Private과 같은 분포의 무작위 표본**으로 구성하면 이 함정이 사라진다. 이 경우 리더보드 공정성 측면에서 더 바람직하다.

## 4. 데이터 통계만으로 점수 올리기 — 대부분 차단됨

| 시도 | 결과 | 판단 |
|---|---|---|
| test 프롬프트·장면이 train과 겹치는가 | 0건(문장, 장면 구성 모두). test 내부 중복도 0건 | 암기 불가 |
| 가장 비슷한 train 프롬프트의 이미지로 이미지-이미지 검색 | 단독 0.01–0.02, 코사인과 결합 시 최대 +0.004 | 효과 없음 |
| 이미지만 보고 HN 판별(L2) | AUC 0.55, prior로 쓰면 하락 | 효과 없음 |
| 파일 크기, 밝기, 색 통계로 HN 판별 | AUC 0.50–0.54 | 효과 없음 |
| 프롬프트 길이·문체로 정답 추정 | 문체 가이드는 묶음 안에서 배정되며 이미지와 무관 | 근거 없음(미측정) |
| top-5 순서 헤지 | 정답이 1개라 다양화 이득 없음(쌍둥이 헤지 −0.005) | 효과 없음 |

## 5. 정당하지만 공정성에 영향을 주는 경로

규정 위반은 아니지만 운영진이 미리 알고 있어야 할 것들이다.

- **생성기를 이용한 학습 데이터 증강.** 이미지 생성 모델(Qwen-Image-2512 + Lightning)은 공개 모델이다. 참가자가 생성기를 추정하면 train 프롬프트를 변형해 같은 분포의 이미지와 HN을 무한히 만들 수 있다(8-step이라 GPU 1장으로 16시간에 수만 장). 정당한 딥러닝이지만 **연산 자원 격차**가 점수 격차로 이어진다.
- **추론 시점 재생성.** test 프롬프트로 이미지를 다시 생성해 픽셀 비교하는 방법은 8,000장 생성이 15분 안에 불가능하므로 현실성이 낮다. 다만 시드 규칙(`base_seed + sha256("<split>:<id>")`, `base_seed = 20261103`은 날짜 형태)이 알려지면 위험해진다. stage3 코드 비공개를 유지하고 다음 생성부터는 무작위 base_seed를 권한다.
- **묶음 크기 가변화(김우진 제안).** 묶음을 4–20장으로 다양화해도 텍스트로 묶음을 복원하는 것과 묶음 단위 배치 학습은 그대로 가능하다. 따라서 §2의 허점을 막지는 못한다. 난이도 분포를 넓히는 효과는 기대할 수 있다.
- **30회 제출로 Public 탐색.** 문항 일부만 바꿔 제출하고 점수 차이로 정오를 알아내는 탐색은 30회로는 수십 문항 수준이라 실익이 작다.

## 부록: 재현

측정은 `baselines/chan_lee/cache/emb/`의 SigLIP2 임베딩 캐시(zs, `b2_siglip2_bundle`)만으로 수행하였다. 이미지와 모델 가중치는 필요 없다. 문항 간 정규화는 유사도 행렬 S(8,000 × 15,000)에 대해 다음과 같이 계산하였다.
- inverted softmax: `S/τ − logsumexp_over_queries(S/τ)`
- CSLS: `2S − (이미지별 상위 10개 문항 유사도 평균) − (문항별 상위 10개 이미지 유사도 평균)`
- 쌍둥이 검출: 이미지 임베딩의 상호 최근접 이웃(코사인 > 0.9)
