## 1. 지금까지 확인한 사실

### 1.1 데이터 (`data/`, git 제외)

| 항목 | 내용 |
|---|---|
| 받은 파일 | `test_v1.tar` 13.0GB(완료), `train_v1.tar` 3.8GB(다운로드 중) |
| test 구조 | `test_v1/images/00000-07999/*.png`(원본 8,000), `test_v1/images/08000-14999/*.png`(HN 7,000), `test_v1/prompts.jsonl` 15,000행 |
| prompts.jsonl | 키가 `{id, prompts}`. 원본 행은 레포의 `test_prompts_v2.jsonl`과 **문장이 완전히 같고 id도 같음**(파일 `00000.png` = 프롬프트 `0000`의 정답). HN 행은 `"prompts": "hard_negative"`라는 표시만 있음 |
| HN 출처 | 패키지에는 **어느 원본에서 만든 HN인지 기록이 없음.** 레포의 variants 8,000개 중 7,000개가 쓰였을 텐데 어느 것인지도 알 수 없음. 그래서 Public 1,000문항(HN이 없는 문항)도 이 패키지만으로는 알 수 없음 |
| 생성 모델 | `stage3` 설정상 train과 test 모두 `Qwen/Qwen-Image-2512` + Lightning 8-step LoRA, 768×768. 시드는 `base_seed + sha256("<split>:<id>")` |

### 1.2 출제 구조 (stage1 코드로 확인)

- test 8,000문항은 '기준' 800문항과 8개씩 묶인 '유사 묶음' 900개(7,200문항)로 이루어진다. train은 '기준' 400문항과 묶음 450개(3,600문항)다. stage1의 `partition()`으로 정확히 복원된다.
- 한 묶음 안의 8문항은 배경, 화풍, 시점, 총 개수가 같고 객체, 개수 배분, 속성, 관계만 서로 다르다. **HN이 없어도 정답마다 같은 묶음의 혼동 후보 7장이 있다.**
- HN 프롬프트는 원본에서 슬롯 하나를 바꾼 것이다(test의 96%). 바뀌는 슬롯은 개수(two→three), 방향(left↔right, above↔below), 그리고 **속성(재질·색·무늬·자세)**이다. 속성 교체가 가장 많다.
- HN 프롬프트가 다른 문항의 프롬프트와 똑같거나 단어 구성이 같은 경우는 0건이다. 그래서 HN이 다른 문항의 정답이 되는 라벨 충돌은 텍스트 수준에서는 없다.

### 1.3 이미 드러난 누수 위험 (**배포 전에 반드시 고쳐야 함**)

1. **파일명 = 정답.** 원본 이미지의 파일 id가 프롬프트 id와 같다. 이 패키지를 그대로 배포하면 프롬프트 id를 이미지 id로 바꾸기만 해도 만점이다.
2. **폴더와 id 범위로 HN이 구분된다.** `08000-14999`에 있으면 모두 HN이다. HN을 후보에서 빼기만 해도 Private 점수가 크게 오른다.
3. **prompts.jsonl의 `hard_negative` 표시**가 그대로 남아 있다.
4. 시드가 `split:id` 해시로 정해진다. HN을 원본과 같은 id로 생성했다면 초기 노이즈를 공유해, 원본과 HN이 거의 같은 구도의 쌍이 된다. 그러면 이미지끼리 비교하는 것만으로 쌍을 찾을 수 있다(4.3절 L4에서 측정).

→ 참가자 배포본에는 다음이 필요하다(리포트 권고안에 포함).
- 무작위 id로 바꾸고 이미지 순서를 섞는다.
- 폴더 하나로 평탄화한다.
- prompts에서 HN 행을 제거한다.
- PNG 메타데이터를 제거한다.
- 원본과 HN의 파일 크기·압축 분포를 맞춘다.

## 2. 평가 조건

| 이름 | 문항 | 후보 풀 | 용도 |
|---|---|---|---|
| `test` | 8,000 | 15,000(원본 8,000 + HN 7,000) | **본 결과.** 운영진이라 정답을 알고 있으므로 test에서 직접 잰다 |
| `test` Public | 1,000 | 위와 같은 풀 | 해당 문항의 HN은 풀에 없음 |
| `test` Private | 7,000 | 위와 같은 풀 | 해당 문항의 HN이 풀에 있음 |
| `val` | 500(train 묶음 단위로 분리) | 그 500장 + 해당 train HN(현재 102장) | B2 학습 중 모델 선택, L2 검증 |

- **Public/Private 정의.** 공식 목록이 없다. 그래서 HN 이미지와 그 출처 원본을 이미지 유사도로 짝지어 복원한다(3.1절). 짝이 없는 원본 1,000장이 Public 문항이다. 복원에 실패하면 지금 쓰는 잠정 규칙(기준 800 + 무작위 200)을 유지하고, 결과에 `public_split_provisional: true`로 표시한다.
- **불확실성.** 점수마다 문항 단위 bootstrap 95% CI를 함께 낸다(1,000회). 부분집합(400문항 등)으로 잰 값은 CI 폭이 약 ±0.04다. 그래서 작은 차이는 결론 근거로 쓰지 않는다.
- **진단 지표.** 오답일 때 top-1이 무엇인지 나눠 집계한다.
  - 자기 HN
  - 같은 묶음의 다른 원본
  - 그 원본의 HN
  - 기타

  이 분류로 어려움의 원천을 분리한다. 핵심은 HN 때문인지, 묶음 구조 때문인지다.

## 3. 단계별 작업

### 3.0 데이터 준비 (11/9 오후, 약 40분)

1. **압축 해제 전에 목록을 검사한다**(test 완료, train 예정). 경로 탈출이나 절대경로 항목이 없는지 본다. test는 0건이었다.
2. `data/test_v1/`, `data/train_v1/`로 압축을 푼다. `configs/paths.yaml`의 이미지 패턴을 실제 구조(`images/<범위>/<id5>.png`)에 맞추고, HN 이미지 목록을 따로 읽는 로더를 추가한다.
3. **HN ↔ 원본 짝 복원.** 작은 해상도(예: 64×64)의 픽셀 거리와 SigLIP2 이미지 임베딩 nearest-neighbor로 HN마다 원본을 찾는다.
   - 신뢰도 확인 1: 1등과 2등의 거리 비율
   - 신뢰도 확인 2: 짝지은 원본의 variants 프롬프트와 HN 이미지의 텍스트-이미지 유사도가, 원본 프롬프트보다 높은지
   - 산출물: `cache/meta/test_hn_sources.json`(git 제외, 기밀). Public 1,000 목록도 여기서 나온다.
4. **누수 검사 스크립트** `scripts/check_leaks.py`
   - 파일명과 정답의 관계
   - PNG chunk(tEXt/iTXt/eXIf)
   - 파일 크기와 압축률 분포(원본 vs HN), 이미지 해상도와 모드
   - tar 내부 순서와 mtime

   결과는 `results/l0_leak_audit/`에 둔다(수치만, 문항 원문 없음).
5. **train/test 생성기 동일성 확인.** 동결 임베딩으로 "train 이미지인가 test 이미지인가" 분류기(linear probe)를 학습한다. AUC가 0.5 근처면 같은 생성기다. 높으면 domain shift가 있다는 뜻이므로, 유료 모델로 다시 만들었다는 이야기가 사실인지 확인 요청한다.

### 3.1 B1: Zero-shot dual encoder (11/9 저녁~밤, MPS 약 3~4시간, 백그라운드)

| exp | 모델 | 크기 | 비고 |
|---|---|---|---|
| `b1_clip_l14_336` | OpenAI CLIP ViT-L/14@336 | 0.43B | 고전적 기준 |
| `b1_openclip_h14` | OpenCLIP ViT-H/14 LAION-2B | 0.99B | |
| `b1_dfn5b_h14_378` | DFN5B ViT-H/14@378 | 0.99B | |
| `b1_eva02_l14_336` | EVA02-CLIP-L/14@336 | 0.43B | |
| `b1_siglip2_so400m384` | SigLIP2 so400m/16@384 | 1.1B | 유력한 1위 후보 |
| `b1_pecore_l14_336` | Perception Encoder Core L | 0.67B | |
| `b1_metaclip2_h14_378` | MetaCLIP2 H/14@378 | 1.0B | |
| `b1_qwen3vlemb_2b` | Qwen3-VL-Embedding-2B | 2B | VLM 기반 임베딩(2026.1) |
| 큰 모델(3.6절) | bigG, PE-Core-bigG, Qwen3-VL-Embedding-8B | 2.5~8B | |

- **측정 항목**: test 전체 점수(Public/Private/기준/묶음), Recall@K 곡선(K=1~100), 시간, 피크 메모리.
- **Recall@K 곡선이 B3의 상한을 정한다.** 1단계가 K 안에 정답을 넣지 못하면 재정렬기가 아무리 좋아도 맞힐 수 없기 때문이다.
- 임베딩은 캐시(`cache/emb/`)한다. 그래서 같은 임베딩으로 L1, HN 수 조절, 재정렬 실험을 다시 인코딩 없이 돌린다.
- **추정 시간(MPS, 추정치)**: L/H급은 모델당 test 15,000장에 5~10분, 2B VLM 임베딩은 20~30분이다.

### 3.2 난이도 조절 시뮬레이션: test HN 수 (B1 캐시로, 10분)

- **질문 4용.** 후보 풀의 HN을 0 / 1,750 / 3,500 / 5,250 / 7,000장으로 무작위로 줄이면서 B1 상위 3개 모델의 Private 점수 곡선을 그린다. 이미지를 새로 만들지 않고 "HN 수를 바꾸면 점수가 얼마나 변하는가"에 답할 수 있다.
- 같은 방식으로 "묶음 효과"도 분리한다. 기준 문항과 묶음 문항의 점수 차이, 그리고 오답 top-1 분해를 본다.

### 3.3 B2: 파인튜닝 (11/10 오전, 조건당 30~60분 추정)

- 대상: B1 1위 모델(SigLIP2 예상). 마지막 4블록과 head만 학습하고 bf16을 쓴다. 3,500쌍으로 약 5 epoch.

| exp | 설정 | 비교 목적 |
|---|---|---|
| `b2_*_inbatch` | 무작위 배치, in-batch negative만 | 기본 |
| `b2_*_bundle` | 묶음 8개를 한 배치에 넣어 hard in-batch negative | 참가자가 쉽게 떠올릴 개선. 묶음은 텍스트로 복원 가능 |
| `b2_*_bundle_hn` | 위 설정 + train HN(학습용 약 398장)을 추가 negative로 | **질문 3의 근거**: `bundle_hn - bundle`의 Private 점수 차이 |

- 평가는 val과 test 양쪽에서 한다. val의 HN이 102장뿐이라 HN 효과는 test Private에서 판단한다.

### 3.4 B3: 2단계 재정렬 (11/10 오후~밤, 가장 오래 걸림)

**측정 방법(시간 절약)**
- 재정렬 점수는 쌍마다 독립이다. 그래서 1단계 top-50을 한 번만 채점해 두면, 같은 점수로 K = 5 / 10 / 20 / 50 곡선을 모두 얻는다.
- MPS로 8,000 × 50 = 40만 쌍을 채점하는 것은 불가능하다. 그래서 **Private 300 + Public 100 = 400문항 층화 부분집합**에서 잰다. 시간은 쌍당 처리량으로 전체 규모에 환산한다.

| 후보 재정렬기 | 크기 | 방식 |
|---|---|---|
| Qwen3.5-0.8B / 2B / 4B / 9B | 0.8~9B | Yes/No 로짓 차(VQAScore 방식) → 크기에 따른 곡선 |
| Qwen3-VL-Reranker-2B / 8B | 2B / 8B | 전용 멀티모달 cross-encoder(2026.1) |

- 이미지 해상도(`max_pixels`: 256² / 448² / 768²)도 속도와 정확도를 함께 바꾸는 손잡이다. 최상위 재정렬기 하나로 비교한다.
- **추정 처리량(MPS, 추정치)**: 2B는 초당 약 10쌍, 9B는 초당 약 2~3쌍이다. 400 × 50 = 2만 쌍이면 2B는 약 35분, 9B는 약 2~3시간이다. 9B는 K_max를 20으로 줄일 수 있다.

### 3.5 B4: 슬롯 검증 재정렬 (선택, 시간이 남으면)

- 프롬프트를 슬롯(객체, 개수, 속성, 방향)으로 파싱한다. 이 데이터는 템플릿이 규칙적이라 규칙 기반 파서로 충분하다.
- 그다음 OWLv2 / Grounding DINO로 개수와 좌우·상하 관계를 검증해 재정렬 점수에 더한다.
- HN의 주된 변경이 속성이라, 검출기만으로는 효과가 제한적일 것으로 예상한다. B3보다 우선순위가 낮다.

### 3.6 큰 모델 (나에게 배정된 몫, 11/10 밤 백그라운드)

- "제한이 없을 때 24GB 안에서 도달할 수 있는 상한"을 잰다. **질문 2의 근거**다.
- 1단계 후보: OpenCLIP bigG(2.5B), PE-Core-bigG-14-448, Qwen3-VL-Embedding-8B.
- 2단계 후보: Qwen3.5-9B(bf16 약 18GB), Qwen3-VL-Reranker-8B.
- 1단계와 2단계를 따로 실행하는 구성(`pipeline.py`는 재정렬 전에 1단계 모델을 해제함)으로 피크 메모리가 24GB 이하인지 기록한다.
- **24GB를 넘는 모델**(Qwen3.8-27B 등)은 bf16로 약 54GB다. 4bit 없이는 들어가지 않아 24GB 규정이 실제로 막는 대상이다. MPS 메모리(36GB)로는 4bit 실험만 가능하다. 그래서 "규정이 없으면 이 모델이 들어온다"는 정성적 근거로만 쓰고, 측정은 생략할 수 있다.
- **bf16 vs 8bit**: bitsandbytes 8bit는 CUDA 전용이다. MPS에서는 측정할 수 없으므로 "측정 불가"로 명시한다.

## 4. 규정 허점 탐색 (category = loophole, honest와 분리 기록)

| exp | 방법 | 금지 조항 | 비용 |
|---|---|---|---|
| `l1_hungarian_*` | 전체 유사도 행렬에 top-50 희소 Hungarian(1:1 할당) | 문항 간 정보 활용 | B1 캐시로 수 분 |
| `l1_greedy_*` | greedy 1:1 할당 | 같음 | 수 분 |
| `l1_bundle_*` | 묶음(8문항) 안에서만 Hungarian. stage1 정답 묶음을 쓴 상한과 **텍스트로 복원한 묶음**(배경·화풍·시점·총 개수 일치) 두 가지 | 같음 | 수 분 |
| `l2_hn_detector_*` | 원본/HN 이진 분류기(동결 임베딩 linear probe + 파일 크기 등 단순 통계)를 이미지 prior로 사용 | 출제 의도 우회(문항 간 정보는 아님) | 30분 |
| `l3_text_*` | 텍스트만으로 얻는 지름길: 프롬프트 id ↔ 이미지 id, 묶음 복원, 템플릿 편향 | 누수 | 30분 |
| `l4_twin_pairs` | 이미지끼리 near-duplicate 쌍을 찾아 "쌍이 있는 이미지 = HN 또는 그 원본" 정보 활용 | 문항 간·이미지 간 정보 | 30분 |

- **L2 판단 기준**: test HN 탐지 AUC와, prior를 더했을 때의 Private 점수 상승. AUC가 높으면(예: > 0.8) 생성 아티팩트로 HN이 구분된다는 뜻이다. 그 경우 train HN 500장 제공은 이 공격의 학습 데이터를 주는 셈이므로, 질문 3의 권고에 반영한다.
- L1의 이득이 클수록 "문항 간 정보 활용 금지" 조항과 함께 탐지 방법이 필요하다. 탐지 방법 후보는 두 가지다: 채점 서버가 문항을 섞어 한 개씩 독립 실행하는 방식, 그리고 제출 랭킹의 top-1 중복률 검사.

## 5. 회의 질문별 판단 방법

### 5.1 질문 1: 추론 시간 제한

- 산출물: 점수 vs 총 추론 시간 산점도와 파레토 프런티어(`results/figures/pareto.png`). 대상은 B1 단독, B1 + B3의 K별 조합, 큰 모델 구성이다.
- 표: 시간 10 / 20 / 30 / 60분 각각에서 도달 가능한 최고 점수와 그 구성.
- **권고 기준**:
  - 1단계만 쓰는 최고 점수와 그 시간 안에서 2단계를 쓴 최고 점수의 차이가 충분히 커야 한다. 그래야 2단계 설계가 보상받는다.
  - 동시에 "대형 VLM으로 전수 비교"는 그 시간 안에 불가능해야 한다.
  - 이 두 조건을 함께 만족하는 가장 짧은 시간을 권고한다.

### 5.2 질문 2: 모델 크기·용량 제한

- 24GB 안의 최상위 구성 점수가 시간 제한 안에서도 거의 만점(예: Private 0.9 이상)이면, 시간 제한 외에 크기 제한이 추가로 필요하다고 권고한다.
- 반대로 상한이 낮으면 시간 제한만으로 충분하다고 권고한다.

### 5.3 질문 3: train HN 500장 제공

- 근거는 두 가지다: B2 `bundle_hn - bundle`의 Private 점수 차이, 그리고 L2 탐지기의 성능.
- **권고 기준**:
  - 차이가 작고 L2 위험도 낮으면 → 제공한다. 공정성과 학습 편의를 위해서다.
  - L2가 강하면 → 제공하지 않거나, 아티팩트를 줄인 뒤 제공한다.

### 5.4 질문 4: 난이도(HN 7,000)

- 3.2절의 HN 수 곡선, Public과 Private의 점수 차이, 오답 top-1 분해를 근거로 쓴다.
- "honest 최상위 Private 점수가 너무 높거나(변별력 없음) 너무 낮은(우연 수준)" 구간을 피하는 HN 수를 제시한다.

### 5.5 질문 5: 규정 허점

- 4절 표의 방법별 점수 이득 + 1.3절의 누수 목록 + 막는 방법을 함께 정리한다.

### 5.6 시간 수치에 대한 주의 (MPS로만 측정)

- 모든 시간은 MPS(M4 Max) 실측값으로 기록한다(`timing.device = mps:M4Max`).
- 24GB CUDA GPU 환산치는 **추정**이라고 명시한다. 환산 방법은 다음과 같다.
  - 같은 모델의 공개 벤치마크 처리량 비율로 계산하거나
  - CUDA 장비를 1~2시간 쓸 수 있으면 `scripts/predict.py`로 대표 구성 3~4개만 실측한다(권장).
- 규정 수치(몇 분)는 최종적으로 CUDA 실측으로 확정해야 한다고 리포트에 적는다.
